# Material Fidelity Plan

Goal: in Game render mode, draw each material as close to the game's own output as possible, and have a
**programmatic** answer to two questions, per game:

1. **What needs supporting?** Which shaders and shader features exist, and how much of the game uses each.
2. **What is wrong?** Which materials Smithbox draws differently from the game, and in what way.

Primary targets are ER, NR and AC6 (MATBIN + DXIL shaders, shader tables already exist). DS3 / SDT / BB
(MTD, `g_` sampler names) follow in Phase 7. DES has its own path (`Older Games/`) and is out of scope.

Status (2026-11-08): Phase 1 done. `Tools/MaterialSurvey` has run on ER, NR and AC6; results and findings are in
[Census/README.md](Census/README.md). It confirmed that MetallicMap is dropped in all three games, and found that the
name fallback binds some MetallicMaps as albedo when the shader name contains "Albedo" (since fixed).
Phase 2 done: `Tools/ShaderSignature` has signatures for every ER/NR/AC6 shader and permutation
([Signatures/README.md](Signatures/README.md)), and the G-buffer layout is decoded in [GBuffer.md](GBuffer.md).
The biggest finding is that F0 is 0 for these games in Smithbox, while the game uses `mix(0.04, albedo, metallic)`.
Permutations are chosen by `GXFT_SATStaticSwitch`. The checked-in recipes match the shaders' slots in 96–99% of
entries. Recipe regeneration was replaced by that consistency check (see the README).
Phase 6 metallic work built: metallic path, offsets, per-layer pairing (GBuffer.md), not yet checked in the app.
Phase 3 done: `MaterialBinding.Route` is the shared routing decision, and the census audits every texture against
`Signatures/{GAME}_SlotMeanings.json` (Census/README.md, Binding audit). Ok is 80% (ER), 74% (NR) and 52% (AC6) of
placed texture-triangles. Per-layer UV sets fixed (`{GAME}_UvSets.json`). The audit now models slot occupancy, which
shows the biggest remaining gaps are layered shaders whose extra layers are never drawn: `C[DetailBlend]`,
`M[AMSN_V][Ov_AN]`'s overlay, and AC6's `[MS]` blends. The `Ov_AN` overlay is now fixed (`{GAME}_Overlays.json`).
Blend-recipe generator built (`ShaderSignature blends`, `{GAME}_GeneratedBlends.json`, Signatures/README.md). It
reproduces 60/97 ER recipes and adds 38 ER, 49 NR and 52 AC6 recipes. NR Ok is now 76.9%, ER 80.3% (audit not rerun
after the last 11 TEXCOORD2/3 recipes). Colour-only layers, any-TEXCOORD vertex sources (two at most) and the extended per-layer blend form are built, so AC6
`[MS]` blends have recipes. AC6 Ok is now 57.3% (was 47.2%). `C[DetailBlend]` detail stacks are built (`ShaderSignature detailstacks`,
`{GAME}_DetailStacks.json`, Signatures/README.md), including whole-albedo layers and back faces. They are not yet
checked in the app. `[S2]` and `_SSS` are covered as well. ER Ok is now 83.7% and NR 80.9%. The `ColorAdjust` weight
form is built (`ShaderSignature coloradjust`, `{GAME}_ColorAdjust.json`), not yet checked in the app; it fixes weight
maths, which the audit doesn't measure. The blend generator now reads that form too, so `M[Cave_001]`, `M[Cliff_001]`
and others have recipes. Crystal-style glow masks route as emissives (`ShaderSignature emissivemasks`). Snow layers
(facing source) and fur's masked layer are built; SSS and Grass2 masks have nothing to draw into. ER Ok is now 85.1%
and NR 83.1%. Still left: AC6's `[MS]` permutations with no recipe (two-vertex and facing weights), which is
where its dropped masks come from. Then Phase 4.

## 1. Where things stand

### What exists

| Piece | Where | What it does |
|---|---|---|
| `MaterialDefinition` | `Renderer/Materials/MaterialDefinition.cs` | Resolves one MTD/MATBIN into samplers (role, slot, tiling, colour, scroll), blend layers, overlay, magma, water, fur, deformer |
| Shader table | `Assets/Material Definitions/{GAME}.json` | Hand-written per-shader deformer / blend-weight / param roles |
| Generated recipe tables | `{GAME}_TextureGroups / _TextureInputs / _Blends / _Details / _Magma / _Water / _Fur.json` | "Generated by analysing the game's compiled pixel shaders" |
| `MaterialMetaparam` | `Renderer/Materials/MaterialMetaparam.cs` | Reads UV groups from `.metaparam` |
| Material Definition Dumper | `Developer/Tools/MaterialDefinitionDumper.cs` | Dumps resolved definitions + a per-shader TSV (Materials, Shader, Known, Deformer, BlendLayers, BlendWeight) |
| Texture binding | `FlverResource.ProcessMaterialTexture` / `LoadBlendRecipe` | Recipe path first, then **name matching** on `ALBEDO / NORMAL / SPECULAR / SHININESS / BLENDMASK / Emissive` |
| Shading | `FlverShader.frag` | One surface model: albedo, normal.xy, roughness = `1 - normal.z` (or a shininess map on BB/DS1/DS2), F0 = specular map |

### Gaps found while surveying

- **The recipe generators are not in the repo.** The `_Blends`, `_Details`, `_Water`, `_Fur`, `_Magma`,
  `_TextureInputs` tables were produced by analysis code that lived outside the repo (likely a scratchpad), so
  they cannot be re-run or extended. Only `GenerateTextureGroups` (metaparam) is reproducible.
- **No `MetallicMap` handling anywhere.** `ProcessMaterialTexture` falls through on any role that is not albedo,
  normal, specular, shininess, blend mask or emissive, so it is silently dropped. If ER/NR/AC6 materials name
  their third texture `MetallicMap` (to confirm in Phase 1), every such material gets the default F0 texture.
- **Per-game shading falls back to DS3.** `FlverShader.frag` defines game IDs only up to `GAME_SEKIRO`; ER, AC6,
  NR, DB take the `else` branches. Whether that is right (normal.z = gloss, specular map = F0) is unchecked.
- **The dumper's "Known" means "has a table entry"**, not "rendered correctly". A shader with no entry can draw
  perfectly; a shader with an entry can still drop textures.
- **Nothing records what was dropped.** A texture with no destination produces no log, no stat, no colour.

## 2. Approach

Three layers of evidence, cheapest first. Each is useful alone; together they give a ranked, re-runnable
worklist.

```
          game shaderbdle (.ppo DXIL)            game MATBINs + FLVERs
                     │                                     │
       ┌─────────────▼─────────────┐          ┌────────────▼────────────┐
 (B)   │ Shader Signature Extractor │          │  Material Census     (A) │
       │ textures read, channels,   │          │  usage weighted by mesh  │
       │ where each one goes        │          │  count / map coverage    │
       └─────────────┬─────────────┘          └────────────┬────────────┘
                     │        expected                      │ actual
                     └──────────────►  Binding Audit  ◄─────┘
                                       (per material: consumed / dropped /
                                        misread channel / unknown feature)
                                            │
                     (C)  Reference Oracle  │  pixel diff of G-buffer channels
                          game PS via       ▼
                          dxil-spirv  ──►  Coverage Report  ──►  ranked worklist
                                            │
                                            ▼
                               in-app: Developer tab + viewport overlay
```

- **(A) Census** answers *what needs supporting* by usage.
- **(B) Signature + Binding Audit** answers *what is wrong* statically: everything the game's shader reads that
  Smithbox does not, or reads differently.
- **(C) Oracle** answers *what is wrong* numerically, by running the game's own pixel shader on the same inputs
  and diffing.

## 3. Phases

### Phase 1: Material Census (what needs supporting)

New tool `Tools/MaterialSurvey` (C#, references SoulsFormats + Andre.IO, ER through the VFS, setup as in
`Full GI/Tools.md`).

- Walk every FLVER in `map/`, `chr/`, `parts/`, `asset/` (ER: `aeg`), read each material's MATBIN path.
- Count per MATBIN and per shader: FLVERs, meshes, triangles, and which maps reference it (via MSB part models).
- For each MATBIN record every sampler: full name, slot, role suffix (`AlbedoMap`, `NormalMap`, `MetallicMap`, …),
  whether it has a path, and every param name.
- Split shader names into tokens (`ShaderTokens` already does this) and count tokens independently, since
  `[Mb2]`, `[Ov_N]`, `[Sway]` are features shared across many shaders.

Output, per game, in `Documentation/Claude/Material Fidelity/Census/`:

- `{GAME}_Shaders.tsv`: shader, materials, meshes, triangles, maps, tokens.
- `{GAME}_Roles.tsv`: sampler role, count, which shaders use it. This is where `MetallicMap` and any other
  unhandled role show up immediately.
- `{GAME}_Tokens.tsv`: token, triangles covered.

Done when: the top shaders covering 95% of map triangles in ER are listed, and every sampler role in ER/NR/AC6
is enumerated.

### Phase 2: Shader Signature Extractor (what the game reads)

Bring the lost generators back into the repo as `Tools/ShaderSignature`, and broaden them.

- Unpack the `.shaderbdle` binders (the `ivtool shaders` command fails on the nested format; fix that reader).
- For each pixel shader `.ppo`, run `dxc -dumpbin` (Windows SDK, already used) and parse the disassembly:
  - Resource bindings: every `Texture2D_N_*` and its register.
  - For each `sample` / `sampleBias` / `textureLoad`: which texture, which UV expression (`TEXCOORDn`, scaled
    by which cbuffer field), and **which channels are extracted** (`extractvalue %x, 0..3`).
  - Follow each extracted channel forward a bounded number of steps to the `storeOutput` it reaches (SV_Target
    index + component). The G-buffer layout (Phase 2b) turns that into "albedo.r", "normal.x", "roughness",
    "metallic", "emissive" etc.
  - Flags: `discard` (alpha test), dither, use of vertex colour, use of `TEXCOORD1+`.
- Re-emit the existing recipe JSONs from this one pipeline, and diff them against the checked-in ones: they
  must match before anything else is trusted (same rule as the TAE "always roundtrip" memory).
- New output `{GAME}_Signatures.json`: shader → list of `{ slot, role, uv, channels → gbuffer target }`.

**Phase 2b: G-buffer layout.** Decode the deferred G-buffer once per game from the deferred lighting shader
(`gxrenderershader/*` reading the same targets), so `SV_Target1.z` can be named. Document in
`Material Fidelity/GBuffer.md`.

Done when: the generated recipes reproduce the checked-in JSONs exactly, and the top-95% shaders all have a
signature.

### Phase 3: Binding Audit (what Smithbox does with it)

Make Smithbox report its own decisions, then compare.

- In `FlverResource`, record a `MaterialBindingRecord` per material as it binds: every sampler name →
  destination `TextureType`, or `Dropped` with the reason (no role match, no path, recipe rejected it).
  Record which specialisation path was chosen (standard / blend / blendmask / deform, surface, detail, magma).
- Add a headless entry point that runs the same binding logic on a `MaterialDefinition` without a GPU, so the
  audit runs over every material in the census, not only loaded ones. This means pulling the decision part of
  `ProcessMaterialTexture` / `ConfigureMaterialShader` into a pure function both paths call.
- Per material, compare against the signature and classify each texture:

| Status | Meaning |
|---|---|
| `Ok` | Read, to the same G-buffer channel the game writes |
| `Dropped` | The game reads it, Smithbox binds it nowhere |
| `Misrouted` | Bound, but to a different meaning (e.g. metallic read as F0 colour) |
| `ChannelMismatch` | Right texture, wrong channel (e.g. roughness from normal.z vs. from `.a`) |
| `UvMismatch` | Different UV set or tiling expression |
| `Unsupported` | Uses a feature Smithbox has no path for (named by token) |
| `Approximate` | Deliberate stand-in (`MaterialSurface.Water`, `Unlit`, `Fur`) |

- Output `{GAME}_Audit.tsv` and roll it up into the Coverage Report: per shader, `% triangles Ok`, and the
  status counts weighted by triangle count from Phase 1.

Done when: every ER material has a status per texture, and the report ranks issues by triangles affected.

### Phase 4: Coverage Report and in-app surfacing

- Extend the Developer panel's Material Definition Dumper into a **Material Coverage** tab: loads the
  report, sorts by impact (triangles × severity), filters by status / token / shader, and has "find a model
  using this" (the verification-target memory: name a model per feature).
- Add a **Material Coverage** debug view to the viewport's surface views (beside Normals): tint each mesh by its
  worst status (green Ok, yellow Approximate, orange Misrouted/Channel/UV, red Dropped/Unsupported). This lets
  a map be scanned by eye for the remaining problems. The colour comes from a per-material status value in the
  material buffer.
- Check the report into `Material Fidelity/Report/{GAME}.md` with a date, so each fix shows as a diff in the
  numbers.

### Phase 5: Reference Oracle (numeric correctness)

The static audit says *which* inputs differ; the oracle says *how much the pixels* differ, and catches maths
errors the audit cannot (wrong blend curve, wrong tint scale like the `4.55` constants).

- Translate the game's DXIL pixel shaders to SPIR-V with **dxil-spirv** (the translator vkd3d-proton uses; ER,
  NR and AC6 run on Proton through it, so these exact shaders are known to translate).
- Build a harness in `Tools/MaterialOracle` (Veldrid, offscreen) that for one material:
  1. Draws a fixed test mesh (a flat quad and a sphere with tangents, `TEXCOORD0..3` and vertex colour set)
     with the **game's** translated PS, the material's textures bound by slot, and its MATBIN params written
     into the material cbuffer at the offsets from DXIL reflection. Scene cbuffers get fixed neutral values.
  2. Draws the same mesh with Smithbox's `FlverShader` (G-buffer outputs `fsout_surface`, albedo, glow),
     using the same binding code as Phase 3.
  3. Decodes both into the same channels (albedo, normal, roughness, metallic/F0, emissive, alpha) using the
     Phase 2b layout, and reports per-channel error (mean / 95th percentile / max) plus difference images.
- Run it over the top shaders by impact; add `OracleError` per channel to the Coverage Report.

Limits: lighting is not compared (the game's lighting pass is deferred and scene-driven; GPARAM work covers
it), so this checks the material stage only. Shaders that read depth, scene colour or water simulation stay
`Approximate` by design.

### Phase 6: Fix loop

Work the ranked list. Each fix is: change binding / recipe / shader → re-run Phase 3 (+5 for that shader) →
numbers move in the report → name a model for in-app checking. Likely first items, pending the census:

1. Metallic textures (if confirmed): add a `MetallicTextureResource`, route `MetallicMap`, and give ER/NR/AC6
   their own game IDs in `FlverShader.frag` so their F0 = `mix(0.04, albedo, metallic)` path (if that is what
   the signature shows) does not disturb DS3/SDT.
2. Whatever role or token the census shows covers the most triangles with `Dropped` / `Unsupported`.
3. Channel layout per game (roughness source, normal z use) from the signatures, replacing the DS3 default.

### Phase 7: MTD games (DS3, SDT, BB)

Same pipeline, with MTD instead of MATBIN, `.fpo` / DXBC (SM5) shaders instead of DXIL, and `g_` sampler names.
`dxc -dumpbin` does not read DXBC; use `fxc /dumpbin` or the D3DCompiler disassembler, and dxil-spirv does not
apply (vkd3d's DXBC path or a CPU interpreter would). Plan this once Phases 1-4 have been used on ER.

## 4. Decisions

| # | Decision | Recommended |
|---|---|---|
| 1 | Correctness oracle: static audit only, or also the dxil-spirv reference renders | Build Phases 1-4 first, decide on Phase 5 from what the audit leaves unexplained |
| 2 | Where audit binding logic lives: extracted pure function shared with `FlverResource`, or a copy in the tool | Shared function, so the audit cannot drift from what the viewport does |
| 3 | Fetching dxil-spirv (an external binary or source build) | Only when Phase 5 is approved; needs the user's OK to download |

## 5. Risks

- **DXIL dataflow tracing is bounded.** Channels pass through maths, branches and `phi` nodes; the tracer stops
  after N steps and marks the channel `Traced` / `Untraced`. Untraced channels are what the oracle is for.
- **Cbuffer reconstruction for the oracle.** Reflection is not stripped (Full GI notes), so names and offsets are
  available, but scene-level cbuffers need sensible fixed values; wrong ones show up as identical errors on
  every shader, which is itself a useful signal.
- **Generated tables can diverge.** Phase 2 must reproduce the checked-in recipes before replacing them.
