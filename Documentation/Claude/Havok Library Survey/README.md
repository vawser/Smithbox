# Havok Library Survey: overview

Phase 0 of the [Unified Havok Library Plan](../Unified%20Havok%20Library%20Plan.md). Generated by `Tools/HavokLibSurvey` on 2026-11-06 with `ALL 30 8`: up to 30 containers per category, 8 Havok files per container, spread evenly across each game. There's one report per game in this folder, plus `Golden/<GAME>.txt`: one sample file for each distinct (category, format, class set), to use as the acceptance set for later phases.

Run it again from `src/Smithbox.Data`:

```
..\..\Tools\HavokLibSurvey\bin\Release\net10.0\HavokLibSurvey.exe ALL 30 8
```

Each file goes through read → write → re-read → field-by-field graph compare. **Bytes** means the write is identical to the original. **Fixed** means writing the re-read graph gives the same bytes again.

Options, anywhere after the positional arguments:
- `--core` checks Havok.Core: its registries against HKLib's, and its header sniffing against the survey's own (Phase 1).
- `--typediff` compares every type the files describe with the game's registry (written for DB_NT, see [DB_NT Types.md](DB_NT%20Types.md)).

Since Phase 2 the reports also run the unified tagfile engine (`Havok.Formats`, through the HKLib bridge). The "Unified tagfile engine vs HKLib" section shows whether it reads the same objects as HKLib, writes the same bytes as HKLib (`Unified 2018 legacy` and `Unified 2019` must), and writes the original bytes (`Unified 2018` and `Unified 2019`). For writes that aren't byte-identical it gives the section and item counts that differ.

`--buildregistry` writes a 2015 or 2016 registry into `src/Havok/Havok.Core/Res` from every type section of the game's tagfiles and compendiums. Run it with a large sample so it sees every file, e.g. `SDT 100000 100000 <out> 8 --buildregistry` (about 9 minutes). The "Tagfile layouts" section of each report gives the section tree of each tagfile format, which is where the dialects come from.

**Phase 3 result** (2026-11-06): the generated `Havok.hk2016` and `Havok.hk2015` classes read SDT 744/752 and DS1R 482/482, and rewrite SDT 744/744 and DS1R 479/482 byte-identical.

**Phase 2 result** (2026-11-06): files written byte-identical to the original, HKLib → unified engine: ER 0 → 667/670, NR 0 → 638/642, DB_NT 0 → 123/123 (of the files HKLib reads), AC6 773 → 773/774. Parity with HKLib holds on every file.

## Findings that change the plan

1. **DS1R uses tagfiles (`20150100`), not packfiles.** `HavokTypeUtils.IsHKX2` sends DS1R through `HKX2.PackFileDeserializer`, which can't read them. A 2015 tagfile dialect is needed. Only HKX2's name-matching tagfile reader handles DS1R today.
2. **`IsHKX2` sends DS1 to HKX2 too, and HKX2 reads 0/331 DS1 files** (64-bit pointer asserts in `hkRootLevelContainer.Read`). DS1 only works through SoulsFormats.
3. **DS2 (original) is `hk_2012` 32-bit, and no current library reads it.** DS2S is `hk_2014` 64-bit and only HKX2 reads it. SoulsFormats' `HKXDS2` variation reads 0 DS2S files.
4. **BB isn't DS3:** HKX2 reads only 53% of BB files. The failures are layout differences (`hkRelArray`/`hkArray` positions in collision shapes, the `hkbBehaviorGraph` pointer type). The BB overlay in plan §2.5 is real work, not a formality.
5. **HKX2 drops `hkRelArray` data when writing.** `m_planes` on convex polytope shapes comes back empty (graph diffs on DS3 objects), and 31 DS3 chr physics files can't be re-read after a write. Byte identity with HKX2's output is therefore *not* a good bar for those classes. Use the original file.
6. **SoulsFormats HKX writing is effectively broken from 2014 on.** Files it writes can't be re-read (array capacity/flags written as 0x8000000000000000), and skeleton and spline animation writes throw. Read-only parity with SoulsFormats is enough for hk2010. DES and DS1 writes only need to cover what SoulsFormats can actually write.
7. **HKLib 2018 never writes byte-identical files** (ER/NR: the first difference is at byte 2–3, so the section sizes differ). The graph round-trips exactly, so it's an encoding-choice difference, not data loss. HKLib 2019 *is* byte-identical. The merged tagfile engine (Phase 2) should find out why, using the 2019 path as the reference.
8. **DB_NT needs an overlay registry** (hash mismatches for `hkaSplineCompressedAnimation`, `hknpPhysicsSystemData::bodyCinfoWithAttachment`, `hkbBehaviorGraph`, cloth shapes; missing `CustomManualSelectorGenerator::AdditiveType`). Smithbox lists DB_NT as a Havok Editor game but can't load 83% of its files.
9. **Compendiums are found by id.** AC6/SDT binders hold several compendiums. Tagfiles name theirs in `TCRF`, and compendiums list their ids in `TCID`. Unpacked loose files keep the compendium beside them. 8 SDT `c0010_c5000.anibnd` files use a compendium from a *different* binder (not resolved by the survey).
10. **Old binary tagfiles (`0xCAB00D1E`)** are the behbnd `.hkt` files in DS3 and SDT. No library reads them. They're probably behavior project sources, not loaded by the game. *(verify)*
11. **Performance baseline (average read ms):** HKX2 packfile DS3 7.3; HKLib 2018 ER 15–85; HKLib 2019 AC6 22 with a compendium, 222 without. The no-compendium reads are probably slow because each file's embedded TYPE section is decoded every time. *(verify)*
